# 视觉对等（Visual Parity）：从「占比对」到「画面像」

> 本文件是 2026-11-11 一次真实返工的复盘产物，优先级高于 `stage-gates.md` 里的默认数值。
> 违反下面六道闸门（G0–G5），即使所有阶段门禁全 PASS，成品仍会被判定「很差」。
> 本文件解决「输出怎么验」；输入侧「要还原什么」见 `reference-spec.md`。

## 0. 事故复盘（数字来自实测，不是印象）

一次十阶段全部跑完、8 个 HTML 语法全过、控制台 0 报错、构图占比五项全 PASS 的交付，
被用户判为「很差」，追加批评「没有曲线，没有动漫图里面的优美质感，都是几何图形拼接」。

事后把参考图与成品逐像素对比，得到：

| 指标 | 参考图 | v1 成品 | 判定 |
|---|---|---|---|
| 桌面区钞票亮绿像素占比 | 22.0% | **0.0%** | 主体完全消失 |
| 桌面区前景护手红像素占比 | 14.2% | **36.2%** | 前景框膨胀 2.5 倍 |
| 整体平均亮度 | 105.7 | 85.0 | 偏暗 20% |
| 曲线几何构造次数 | — | ~4（只有 Torus） | 全是 Box + Cylinder |
| AABB 占比门禁 | — | 五项全 PASS | **门禁失效** |

根因不是某个参数调错，是**流程只验证了「包围盒」，没验证「画面内容」**：
包围盒 PASS 只说明主体组的 8 个角点投影落在目标区域，
完全不保证主体没有被前景挡住、颜色对不对、有没有曲线。

## 1. 六道硬闸门（G0–G5）

按顺序执行，任一 FAIL 不得进入下一阶段。

### G0 · 朝向与可见面（Stage 2 定，每阶段复测）

**在评价「像不像」之前，先确认「看不看得见」。**
主体的不可替代特征——钳口的缝、角色的正脸、门洞的开口——必须能在默认机位看到。
看不到时，问题在朝向或机位，**不在轮廓**。

- 判据：把该特征的形态描述单独拿出来，对照截图能指出它在哪；指不出就是 FAIL。
- 做法：一次只反转一个旋转轴，各拍一张，判据写死（见 `camera-and-assembly.md` §2.1）。
- 为什么放最前：几何语言再对、色板再准，特征背对相机就是错的主体。
  本轮实测：钳口朝背面时读作闭合圆面团，在轮廓控制点上连调三轮全部白做。

### G1 · 几何语言（Stage 0 定，Stage 3 验）

参考图是手绘卡通时，**「圆角 / 弧线 / 旋转体」是风格本体，不是装饰**。
只用 `BoxGeometry` + `CylinderGeometry` 拼接，观感必然是「积木」，无论色板多准。

- Stage 0 必须新增【几何语言】字段：逐个数出参考图里的曲线特征
  （心形钳、弧顶箱盖、高背椅、鼓形桶、舵轮、圆角钞票、飘动旗摆、缆绳…），
  并给出「曲线物体 / 全部物体」的下限（默认 ≥ 60%）。
- Stage 2 白模就要用圆角基本体占位，**不要等 Stage 3 才发现几何语言不对**。
- Stage 3 验收：源码中曲线构造调用次数 ≥ 12（`quadraticCurveTo` / `bezierCurveTo` /
  `LatheGeometry` / `TubeGeometry` / `TorusGeometry` / `ExtrudeGeometry` / 自定义 Shape 函数）。
  可由 `assets/parity-check.py` 自动统计。

### G2 · 语义色板（Stage 0 定，Stage 3/5 验）

**禁止把「全图 k-means 主色」直接当材质基色。**
全图聚类会把轮廓描边、暗部阴影、大面积背景一起混进簇中心，
得到的颜色比物体真实固有色暗 40–80 个亮度单位。
k-means 只能用来判断「整体色调倾向」，不能用来给具体材质上色。

正确做法：在参考图上**按语义区域开小框**，每框做 3–5 色聚类取最大簇，
记录 `区域名 / hex / 亮度 / 占比`，至少覆盖：上墙、下墙、地板、桌面、主体、前景、主道具。
材质基色用这个值，再按渲染管线的色阶衰减做**一次性**补偿（写进 CONFIG 注释，说明补了多少）。

| 反例 | 症状 | 处方 |
|---|---|---|
| 全图 k-means 主色当基色 | 墙面/地板整片发黑，亮度比参考低 60+ | 改为语义区域采样 |
| 采样框压在描边或阴影上 | 某个材质突然变脏 | 框取物体内部，取最大簇而非中位数 |
| 色阶最低阶 0.30 以下 | 背光面整片死黑 | 最低阶 ≥0.45，或给大面积面单独补光 |

### G3 · 主体内容可见性（Stage 2 定，每阶段复测）

这是最容易被「占比门禁」骗过去的一项。做法是**颜色分割**：
在主体所在的归一化区域内，统计主体特征色像素占比，与参考图同区域对比。

- 主体占比、前景占比，两者都要报，偏差各 ≤9 个百分点。
- 若主体特征色占比接近 0，**无论 AABB 是否 PASS，一律判 FAIL**。
- 常见死法：为了「不被挡住」把主体往远处推，结果投影上移，反而落进前景的覆盖区；
  或者用主体组整体 `scale.z` 压扁去凑占比，把层次压没。
  **只用平移和单个物体的尺寸调整构图，禁止用非等比整体缩放凑数字。**

**占比超差时的归因顺序**（顺序错了就会砍错东西）：

| 顺位 | 先查什么 | 怎么查 | 本轮实例 |
|---|---|---|---|
| 1 | **构图语义差异** | 参考图该区域有没有留白带、走道、被前景压住的空白？ | 钞票绿 36% 超标，真正原因是参考图桌面中轴有一条露出的蓝绒走道，我们铺成了满毯 |
| 2 | **单件尺寸** | 与参考图同一物体的投影宽高比是否一致 | 票面 0.64 时像餐垫（比例错），缩到 0.44 才回到钞票的宽高比 |
| 3 | **数量与密度** | 前两条都对齐后，才动堆数/散张数 | 撤掉中轴三簇，密度自然回落 |
| 4 | **相机距离** | 整体等比缩放（最钝但最安全） | 后撤 0.16m，红绿占比一起回落 |

前两条能解决的问题，不要用第 3、4 条去凑——凑出来的数字会 PASS，画面会变空。

### G4 · 亮度分布与过曝（Stage 5/9 验）

| 指标 | 阈值 |
|---|---|
| 平均亮度差 | ≤22（参考图基准） |
| 亮度 >250 的过曝像素 | ≤1.5% |
| 亮度 <8 的死黑像素 | ≤2.0% |

点光源离墙面 <0.5m 时会在墙上烧出径向白光斑，叠加 Bloom 后面积可占右上区 24%。
补光点光源必须离墙 ≥1m，或改用方向光/半球光补冷色。

### G5 · 结构与细节（Stage 0 定，Stage 2 与 9 各验一次）

前五道闸门保证「看得见、看着像」，G5 保证「站得住、经得起近看」。
判据来自 `reference-spec.md` §5 的结构六查，与 §2.8 的 P0/P1 细节清单。

| 项 | 判据 | 常见失败 |
|---|---|---|
| S1 支撑 | 每个物体能指出靠什么撑着/挂着 | 吊灯悬空、画框浮在墙前 |
| S2 接触 | 底面/背面贴合支撑面，缝隙 ≤2mm | 桌子插进墙、椅腿陷进地板 |
| S3 尺度链 | 地面→桌→主体→顶→天花板逐段自洽，偏差 ≤8% | 桌高 0.9 配椅座 0.45 |
| S4 透视 | 同一水平面平行线收敛同一消失点 | 桌一点透视、地板两点透视 |
| S5 遮挡 | 遮挡链无循环矛盾 | A 遮 B、B 遮 C、C 又遮 A |
| S6 物理 | 无穿透、无镜像反光方向错误 | 酒桶穿柜体、玻璃反射光位相反 |

- 细节兑现率：P0 = 100%，P1 ≥ 80%。缺一条要在门禁块写「缺哪条、为什么、能否补」。
- **任一条 P0 细节缺失，或六查中有 FAIL，不得交付** —— 这类问题调材质救不回来。

## 1.5 六道闸门与规格书的关系

`reference-spec.md` 的 RCI 表是**输入的验收清单**（要在画面上看到什么），
本文件的 G0–G5 是**输出的验收方法**（怎么证明看到了）。
两者必须对上：RCI 里每条 P0 都应能落到某道闸门或某条结构检查上；
落不上的说明它不可校验，回 Stage 0 重写。

| RCI 类别 | 主要落到 |
|---|---|
| G 构图 | 逐顶点投影门禁 + G3 |
| C 色彩 | G2 + G3 |
| L 光影 | G4 |
| M 材质 | G2 + 材质类别计数 |
| S 结构 | G5 的 S1–S6 |
| D 细节 | G1 + G5 的细节兑现率 |

## 2. 构图度量：逐顶点投影，不要用 AABB 8 角点

`new THREE.Box3().setFromObject(obj)` 取 8 个角点再投影，对第一人称场景是错的：
伸向镜头的手/袖子会把近角撑到画面外，实测报出 `w = 1.049`（超过整幅画面）。
v1 为了让这个数 PASS，把长袖踢出主体组、给主体组加 `scale.z = 0.551`，
数字好看了，钞票被压到桌后、被护手完全遮住。

正确实现：遍历主体组所有 Mesh 的实际顶点，经 `matrixWorld` 变换后逐个 `project(camera)`，
取屏幕坐标 min/max；跳过 `material.side === THREE.BackSide` 的描边外壳；
顶点数 >3000 时按步长抽样。这段代码见 `threejs-recipes.md` 的 `measureFrame`。

度量方法换了，数值口径就变了 —— 此时**容差必须重新校准并在文档写明理由**，
但 `baseline` 目标值（来自参考图实测）不得改动。改目标值去凑 PASS 是自欺。

## 3. 曲线几何最小集

| 需求 | 配方 | 典型物体 |
|---|---|---|
| 圆角实体 | `Shape` 画圆角矩形（`quadraticCurveTo`）→ `ExtrudeGeometry` 带 bevel | 桌、柜、箱、钞票沓、书 |
| 自定义轮廓 | `Shape` + `bezierCurveTo` / `quadraticCurveTo` → `ExtrudeGeometry` | 心形钳、椅背、旗摆、画像剪影、扇角 |
| 旋转体 | `LatheGeometry(profile)`，profile = `[[半径, 高度], …]` | 酒桶、灯罩、杯、瓶、椅柱、舵轮把手 |
| 空间曲线 | `CatmullRomCurve3` → `TubeGeometry` | 缆绳、电话线、木纹、金边、旗绳 |
| 环 | `TorusGeometry` | 舷窗、桶箍、袖口、舵盘 |

**Shape 陷阱（本次实踩）**：`ExtrudeGeometry` 会把**开放轮廓自动闭合并填充**。
想画一条「椅背金色包边」而只给了开放曲线，结果生成一整片黄铜，把红色椅背完全盖住。
做细边一律用 `TubeGeometry` 沿轮廓走，或构造闭合的环形 Shape（外轮廓 + 内孔）。

**UV 陷阱**：`ExtrudeGeometry` 的 UV 是 XY 世界单位而非 0–1，
带 `map` 的贴图（钞票花纹、名牌文字、屏幕画面）必须用标准 `BoxGeometry` 薄片承载，
否则纹理会重复或错乱。圆角负责侧面的体积，薄片负责顶面的图案。

**贴片 z 陷阱（本轮实测，且完全静默）**：挤出体是**居中**的，`depth = 0.196` → 前表面在 `z = +0.098`。
把高光块/暗带放在 `z = 0.054` 是**埋在实体内部**，永远不会被渲染，
表现却是「明明加了明暗，还是平的」，于是继续怀疑光照与材质。
规则：所有贴片 `z = depth / 2 + 0.004`。反过来说，想让某细节只在背面可见，放 `-depth/2 - ε` 即可。
（细节见 `camera-and-assembly.md` §5）

## 4. 描边：径向法线，而不是 mergeVertices

原 `stage-gates.md` 的处方「删 uv → `mergeVertices` → `computeVertexNormals`」
对 Box/Cylinder 有效，但对 `ExtrudeGeometry` 会让正面与侧面法线在圆角接缝处互相抵消，
描边裂成一圈**锯齿状虚线**（放大可见点状断点）。

对含曲线几何的场景，改用**径向法线**：克隆几何 → 求包围球中心 →
把每个顶点的法线替换为 `(position - center).normalize()` → BackSide 外壳沿该法线外扩。
外扩方向处处连续，圆角轮廓描边才是一条不断的线。
薄片仍跳过描边（`BackSide` 在双面几何上会翻面）。

## 5. 可复跑验收脚本

把 `assets/parity-check.py` 与 `assets/parity.json` 一起复制到场景目录，改 `parity.json` 后：

```bash
python parity-check.py ref.jpg preview-final.png --html 09-final.html
```

输出 G1（曲线次数）、G3（主体/前景占比）、G4（亮度/过曝/死黑）的 PASS/FAIL 表，
任一 FAIL 退出码 1。**它不替代逐顶点投影的构图门禁，也不替代 G5 的结构六查**，三张表必须同时通过。

**区域框与特征色必须外置**（这条吃过亏）：
`DESK_BOX`、`GREEN`、`RED` 这类量是**某个场景的语义**，不是通用阈值。
写死在脚本里，换个场景（神社黄昏）会统计「钞票绿」和「护手红」，两项恒为 0% 直接 FAIL，
而脚本本身看起来「跑通了」。`parity.json` 的字段：

```json
{
  "regions": [
    { "name": "桌面区", "box": [0.20, 0.55, 0.85, 0.90],
      "features": [
        { "name": "钞票绿", "predicate": "g>110 && g>r*1.06 && g>b*1.10", "tol": 9 },
        { "name": "护手红", "predicate": "r>110 && r>g*1.6 && r>b*1.6",  "tol": 9 }
      ] }
  ],
  "global": { "lumTol": 22, "overMax": 1.5, "deadMax": 2.0, "curveMin": 12 }
}
```

`predicate` 是 JS 风格的三通道表达式，脚本内用 `eval` 限定命名空间转成函数——
这是刻意的取舍：让 Stage 0 的语义色板能**直接生成**门禁参数，而不是每次手改 Python。

交付前必须给用户看这四样，缺一不可：
1. 参考图 / 旧版 / 新版 **三联并排图**（`compare-v2.png` 之类）；
2. `parity-check.py` 的完整输出表；
3. **RCI 表全量状态**（无 TODO；WAIVED 逐条给理由）与 G5 六查一行结论；
4. 明确列出仍未消除的偏差与原因，不许用「接近参考图」这类无数字的话收尾。
